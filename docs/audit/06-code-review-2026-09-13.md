# Segno code review — 13 September 2026

Reviewed commit `09a3c4b` on the initially clean working tree. This report is the only repository addition; application code was not changed. The review covers the music model and ingestion, practice orchestration, MIDI/audio, persistence, reporting, and relevant SwiftUI/notation bridge paths. It is a source and behavior review, not a physical-piano or visual usability certification.

The app has a solid foundation. Separating MusicXML identity from MIDI timing is useful, the pure matcher/report/scheduler components are testable, and offline operation plus portable song folders suit this product. The highest-value next work is making the feedback and saved data dependable. Many older audit issues have already been fixed: this tree has committed tests, bounds-checked MIDI byte reads, repeat unfolding, a Canvas keyboard, incremental cursor lookups, and explicit MIDI teardown. The July audit should not be read as a current defect list.

**Findings, in priority order**

P1 means fix promptly because it can crash, lose data, or invalidate a core practice result. P2 means a reproducible or directly traceable defect that should be addressed in normal development. Static findings are explicitly distinguished from executed reproductions.

1. **P1 — Valid MIDI input can crash the app.**

   [MIDIInput.swift:203](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/MIDIInput.swift:203>)

   `receive` copies the event list and packet into fixed-size Swift values, then indexes `pkt.words` up to the incoming `wordCount`. CoreMIDI packets are variable length: the SDK explicitly permits more than the declared 64 words. A 65-word packet therefore indexes beyond the copied tuple's buffer. `MIDIEventPacketNext(&packet)` also advances through a local copy rather than the original event list, so multi-packet traversal is unsafe when data extends beyond that copy.

   **Evidence:** the isolated 65-word reproduction crashed. The installed SDK documents the variable-length layout in `CoreMIDI.framework/Headers/MIDIServices.h`, around lines 454–520.

   **Change:** traverse pointers into the original callback buffer for both packets and words, retaining their valid lifetime. Parse complete UMP messages at their declared widths. Add tests with several packet timestamps, more than 64 words, and mixed message types; single-note input tests do not cover this.

2. **P1 — A repeated bar can be graded against notes that never play in the selected section.**

   [PracticeSession.swift:875](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PracticeSession.swift:875>), [Ingest.swift:336](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/Ingest.swift:336>)

   Fusion correctly retains separate performed occurrences with the same written beat. `buildGradeExpected` includes every occurrence whose written beat falls inside the selection, while section playback boundaries use the first occurrence of the written bar. Selecting bar 1 in a two-bar repeated passage can stop playback before its second occurrence while still expecting that second occurrence for grading.

   **Evidence:** in the session harness, perfectly playing the selected occurrence produced **1/2 hits, or 50%**. This is consistent with the repeat fixture's existing time mapping. Selecting later portions of a repeat can also put unrelated written bars inside the continuous playback interval.

   **Change:** define one section playback plan, including performed occurrence identity, and use it for playback, matching, capture, cursor movement, and completion. Specify whether section practice includes written repeats. Add section-level tests to complement the existing whole-score fusion tests.

3. **P1 — “Soft delete” can permanently remove the song and all its practice data.**

   [SongLibrary.swift:132](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/SongLibrary.swift:132>)

   If system Trash and the fallback move fail, the code calls `removeItem` on the original song folder. An unavailable or unwritable fallback Trash location can therefore turn a promised recoverable delete into permanent removal. The folder includes takes, flags, history, and the score pair.

   **Evidence:** direct source trace; no real deletion was attempted.

   **Change:** preserve the original on failure and show the error. Give each trashed copy a unique destination rather than deleting a prior copy preemptively. An explicit permanent-delete operation, if ever added, should be separate.

4. **P2 — Playing early in the count-in earns perfect downbeat credit.**

   [PracticeSession.swift:906](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PracticeSession.swift:906>), [AudioEnginePlayer.swift:498](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/AudioEnginePlayer.swift:498>)

   The playback clock remains at section start for the entire count-in. The matcher accepts notes against that frozen time; `recordWrong: false` suppresses unmatched notes but still credits matches. Playing the first chord several beats early counts as being exactly on time.

   **Evidence:** the simulated count-in-only input received a hit with **0 ms error**.

   **Change:** timestamp input relative to the actual scheduled downbeat and accept only the intended early-entry window. This preserves the recent fix for notes played near the count-in boundary without making the whole count-in a valid downbeat.

5. **P2 — Listening to a take can count as performing it.**

   [PracticeSession.swift:536](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PracticeSession.swift:536>), [PracticeSession.swift:1484](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PracticeSession.swift:1484>)

   Replay calls `previewNoteOn`, which now also feeds the live matching pipeline. Replay buttons are available in Wait mode because they are disabled only during normal playback. The recorded notes can advance the walkthrough and write practice history. They can also trigger an armed “start on first note” transport.

   **Evidence:** replaying a one-note take in Wait advanced the step and recorded a completed pass with no player input.

   **Change:** separate sounding a note from receiving a player's note. Give replay an output-only route, with explicit event origins if useful. Test replay during Wait and while sync-start is armed.

6. **P2 — Changing hands or the section during Grade can corrupt the current pass.**

   [PracticeSession.swift:323](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PracticeSession.swift:323>), [PracticeSession.swift:1253](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PracticeSession.swift:1253>)

   The controls remain available during playback. Changing hands updates sound and visual guidance without rebuilding the existing matcher. Section edits change playback boundaries but leave the old expected notes in place. Finalization then labels the result using the new hand/section settings. Switching rhythm mode does rebuild the matcher, but restarts its expectation for the whole section at the current transport position.

   **Evidence:** starting with both hands, switching to RH, and playing the RH note saved an RH pass that still expected two notes and reported one miss.

   **Change:** capture an immutable pass configuration. Apply edits on the next loop, or explicitly abandon and restart the current pass, including its take. Use the same policy for hands, range, rhythm mode, and tolerance.

7. **P2 — Clean Wait retries retain old trouble bars.**

   [PracticeSession.swift:1119](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PracticeSession.swift:1119>)

   Restart clears `fumbledSteps` and the displayed count, but leaves `mistakes`. `recordWaitPass` derives the recorded trouble bars from `mistakes`, so an earlier slip survives a clean retry. Changing the Wait section or hands similarly rebuilds steps without clearing all pass-specific fault state.

   **Evidence:** the second, clean walkthrough recorded `wrong: 0` together with `missedBars: [1]`.

   **Change:** reset the complete Wait-pass state together. If historical review marks should remain visible, keep them separate from the current pass's faults.

8. **P2 — Save failures are still silent outside metadata.**

   [Take.swift:48](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/Take.swift:48>), [PracticeHistory.swift:72](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PracticeHistory.swift:72>)

   Takes, history, flags, sections, time, and reports discard write errors. `TakeStore.keepIfBest` even returns `true` after a failed write. The session can show a recorded pass or saved change that disappears after reopening the app. Atomic writes prevent partial replacement; they do not establish that a write succeeded. Loading corrupted mutable JSON as an empty collection also risks overwriting surviving data on the next save.

   **Evidence:** saving a best take to a nonexistent parent returned **true**, while loading it returned zero takes. The other write paths were inspected statically.

   **Change:** make durable operations throw or return explicit success/failure, surface failures consistently, retain pending writes for retry, and distinguish a missing file from a corrupt one. Keep failed/corrupt originals available for recovery.

9. **P2 — A library backup can silently omit a song.**

   [SongLibrary.swift:220](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/SongLibrary.swift:220>)

   The staging loop ignores each folder-copy error, then archives whatever was copied. One failed copy can produce a normal-looking backup that is incomplete.

   **Evidence:** direct source trace; no actual library export or failure injection was performed.

   **Change:** fail the export or clearly identify omissions. Include a manifest of expected song IDs and files and verify it before reporting success. A restore/import-backup flow should validate the same manifest.

10. **P2 — Session shutdown does not reliably silence the free-running metronome.**

    [PracticeSession.swift:687](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PracticeSession.swift:687>), [AudioEnginePlayer.swift:574](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/AudioEnginePlayer.swift:574>)

    Shutdown skips `audio.stop()` when playback is already stopped, even though a free-running metronome can still be active. When it does call `stop()`, that method can start free-running clicks again. A SwiftUI-retained old session can therefore keep clicking after a song switch—the exact lifetime case explicit shutdown was intended to handle. Replay cleanup and time flushing also still depend on other callbacks or eventual deallocation.

    **Evidence:** direct lifecycle trace. Existing lifecycle tests check deallocation, not `shutdown()` while a session remains retained.

    **Change:** provide a dedicated audio shutdown operation that always cancels timers and silences outputs without restarting anything. Explicitly stop replay and flush time/capture state before disposing MIDI. Test shutdown while deliberately retaining the session.

11. **P2 — Progress and “mastery” mix incompatible kinds of practice.**

    [PracticeProgressView.swift:148](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PracticeProgressView.swift:148>), [PracticeSession.swift:1033](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PracticeSession.swift:1033>), [PassReport.swift:393](</Users/dayneeastaugh/Documents/xCode Apps/Woodshed/Woodshed/PassReport.swift:393>)

    The mastery grid accepts all passes for a range, including untimed Wait walkthroughs. Rhythm-only passes are persisted as `mode: "grade"`, making tap-along results indistinguishable from pitch grading. Report improvement comparisons only require matching bars, so changing from both hands to RH can produce an apparent improvement and “fixed” bars. Best takes are keyed only by bar range, so a slow one-hand 100% take can prevent a later both-hands 100% take from becoming the stored best.

    **Evidence:** direct aggregation/model trace. These are related instances of missing practice context, rather than separate scoring-algorithm failures.

    **Change:** persist a typed practice context: mode, hands, rhythm-only, tempo, tolerance, and scoring version. Separate Wait completion from Grade accuracy. Define explicit eligibility for section mastery and comparable progress. Preserve legacy records as context-unknown rather than assuming equivalence.

**Refine the existing functionality**

- **Make mastery an explicit musical goal.** Keep encouraging note coverage, but distinguish it from a clean pass. Currently an accuracy-gated drill advances after playing all expected notes even when extra wrong notes are played; the harness confirmed one wrong note plus 100% accuracy advanced 60% → 65%. Consider a configurable wrong-note allowance and timing threshold. Show mastery per hand and at a stated target tempo, preferably across several clean passes.
- **Make take playback faithful.** `TakeNote` records velocity, but replay ignores it and emits the fixed preview velocity. Pedal data is analyzed in memory but is absent from persisted `Take`. Preserve velocity and pedal, separate input/output as above, and add an easy reference-versus-my-take comparison. Otherwise listening back hides precisely the touch differences the app reports.
- **Use “not enough evidence” in feedback.** The report defaults to “balanced and clean” when balance/pedal/touch measurements are absent, and to steady rhythm when no usable timing exists. A hand-only or mostly missed performance should not receive those assurances. Add an unmeasured state and show the sample count when it affects confidence.
- **Calibrate timing against the device.** Input packet timestamps are currently ignored and grading reads the playback clock after delivery to the main queue. Use event timestamps and a small latency calibration flow so UI load and device delay do not look like poor playing. Convert timing feedback to wall-clock milliseconds, or clearly label normalized units: the current musical-second error scales with the tempo slider.
- **Protect musical intent.** Pedal crossing several barlines, louder LH, rolled chords, and uneven spacing can be intentional. Allow a technique or passage goal, exempt marked arpeggios/pedaling where known, and phrase uncertain observations as things to listen for. Add rubato-aware and expected-rhythm-aware analysis before treating these signals as authoritative.

**New functionality worth building**

1. **A short daily practice plan.** Let the player choose 10, 20, or 30 minutes. Assemble a warm-up, two weak passages, and one full run using the existing flags, history, time ledger, and drill machinery. Explain why each item was chosen and allow replacement. This makes existing features easier to use together.
2. **Retention checks for mastered sections.** Revisit a section after a delay and distinguish “clean in today's loop” from “still remembered later.” The first version can work entirely on-device when the app opens; it does not need notifications or cloud services.
3. **Device setup and verification.** Add explicit MIDI input/output selection, a test note, pedal indicator, and connection feedback. The current implementation connects all sources and broadcasts to all destinations, which becomes confusing as soon as a virtual port or second instrument is present.
4. **Backup restore and score replacement.** Complete the existing export feature with previewed restore, duplicate handling, and a way to replace a corrected score pair while preserving or explicitly remapping flags/sections. Preserve the original version until the replacement has parsed and reconciled successfully.
5. **Targeted expression exercises.** After capture fidelity and confidence handling are fixed, add legato/release timing and hesitation exercises. Start with explicit technique goals and clear examples; avoid a single opaque “musicality” score.

**Engineering improvements with the best return**

- Extract a `PassConfiguration` and a pure session state machine before adding more mode combinations. The current 1,828-line `PracticeSession` coordinates matching, drills, recording, replay, storage, timing, and teardown. Extract incrementally by responsibility; a full rewrite is unnecessary.
- Promote the temporary interaction reproductions into committed regression tests. Add coverage for repeat sections, configuration changes, count-in boundaries, replay origins, retained-session shutdown, and persistence failures. The current pure-function tests remain valuable.
- Put metronome state and timer lifecycle under one concurrency owner. Some arrays are already dispatched to `metroQueue`, while other shared fields and timer creation/cancellation are accessed across queues. Resolve the actual ownership boundaries and the current actor-isolation warnings together.
- Add versioned persistence and non-destructive migration before expanding the saved practice context. Keep the file-per-song approach unless real query or multi-device requirements justify a database.
- Validate semantic parser inputs as well as byte bounds: zero divisions/ticks-per-quarter, invalid meter/tempo values, unsupported score forms, and empty scores should produce useful import errors. Expand real-score fixtures beyond the current bundled repertoire and generated scales.
- Refresh stale comments after changes. Several source comments still describe the phase-zero state, no iPad sound bank, or unsupported repeats despite later implementations. Preserve the historical audit, but clearly date current status and link to this review.

**Suggested implementation order**

First fix MIDI memory safety, repeat-section grading, and deletion. Then address the shared pass lifecycle—count-in, replay input, settings changes, and Wait resets—with regression tests. Next make persistence/backup completion truthful and progress comparisons compatible. After those, faithful take comparison and a daily practice plan offer the clearest user benefit.
